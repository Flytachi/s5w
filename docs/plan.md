# S5W — план: сущности, именование, механики

Документ фиксирует **что мы создаём и зачем**, до написания кода.
База — s4w (winter-kernel ^3, nginx + fpm). s5w — winter-kernel ^4, рантайм Swoole,
`X-Accel-Redirect` больше нет: отдача через `ResponseStreamFile` (Range/206/304 из коробки).

Новое относительно s4w:

1. временные подписанные ссылки;
2. папки-«времянки» с меткой очистки (день / неделя / месяц);
3. настраиваемый `Cache-Control` на уровне бакета и папки;
4. сквозное переименование — понятные имена сущностей, таблиц, роутов, классов.

---

## 1. Именование

### 1.1 Сущности

| s4w | s5w | почему |
|---|---|---|
| `Instance` | `Bucket` | это не «инстанс приложения», а изолированное пространство с квотой. Слово знакомо по S3. |
| `InstanceStatus` | `BucketStatus` | следом за сущностью. |
| `Section` | `Folder` | «секция» ничего не говорит; в API/UI это папка. |
| `FileRecord` | `FileEntry` | именованная запись в папке (метаданные + ссылка на контент). |
| `FileBlob` | `Blob` | контент как есть, CAS по sha256. «File» в имени — лишнее. |
| `InstanceToken` | `AccessToken` | токен доступа к бакету. |
| — | `ShareLink` | новое: отзываемая/лимитированная временная ссылка. |
| `FileManager` | `BlobStore` | это не «менеджер файлов», а хранилище блобов (put/get/delete/exists). |
| `MediaService` | `DeliveryService` | отдача файла клиенту. |
| `MediaCache` | `DeliveryCache` | кэш метаданных отдачи. |
| `Api\CacheService` | `TokenCache` | кэш «хеш токена → bucket_id». |
| `Api\AuthContext` | `BucketContext` | request-scoped контекст: какой бакет у запроса. |
| `AuthMiddleware` | `AdminJwtMiddleware` | явно: админский JWT. |
| `DefaultMiddleware` | `ServiceTokenMiddleware` | статический `TOKEN` для эндпоинта логина. |
| `InstanceTokenMiddleware` | `AccessTokenMiddleware` | следом за сущностью. |
| `InstanceCreateJob` | `BucketProvisionJob` | «create» ничего не уточняет; job создаёт каталог и доводит статус. |
| `InstanceDeleteJob` | `BucketPurgeJob` | сносит и БД-строку, и каталог. |
| `OrphanFolderGc` | `OrphanDirSweeper` | «folder» теперь занято сущностью `Folder`; тут именно каталог на диске. |
| `OrphanBlobGc` | `OrphanBlobSweeper` | единый суффикс для фоновых чисток. |
| — | `RetentionSweeper` | новое: удаление просроченных `FileEntry`. |
| — | `ShareLinkSweeper` | новое: чистка протухших строк `ShareLink`. |

### 1.2 Таблицы

Префикса `s4w_` не будет: БД/схема выделены под сервис, префикс — шум.
Имя задаётся явно в репозитории (`public static string $table`), так что свобода полная.

`buckets`, `folders`, `files`, `blobs`, `access_tokens`, `share_links`

### 1.3 Структура кода (`main/`, PSR-4 `Main\`)

```
main/
  Config/        DbConfig
  Entity/        Bucket, Folder, FileEntry, Blob, AccessToken, ShareLink
  Enum/          BucketStatus, TokenStatus, Retention, CacheVisibility, Disposition
  Repository/    по одному на сущность
  Dto/           ответы API (BucketRes, FolderRes, FileRes, TokenRes, ShareLinkRes)
  Request/       валидируемые входные модели
  Service/       BucketService, FolderService, FileService, DeliveryService,
                 ShareLinkService, AccessTokenService, AdminAuthService, CachePolicy
  Storage/       BlobStore
  Http/Admin/    контроллеры /admin       (JWT администратора)
  Http/Api/      контроллеры /v1          (AccessToken бакета)
  Http/Delivery/ контроллеры /o /p /t     (отдача файлов)
  Http/Middleware/
  Job/           BucketProvisionJob, BucketPurgeJob
  Schedule/      RetentionSweeper, OrphanBlobSweeper, OrphanDirSweeper, ShareLinkSweeper
  Web/           админ-панель (контроллеры вьюх)
```

### 1.4 Роуты

| префикс | кто пускает | что |
|---|---|---|
| `/admin/**` | JWT администратора | управление бакетами, папками, токенами, файлами |
| `/v1/**` | `AccessToken` бакета | API арендатора (файлы, папки, выпуск ссылок) |
| `/o/{bucket}/[folder/]{file}` | никто (открыто) | публичная отдача, только `public = true` |
| `/p/[folder/]{file}` | `AccessToken` бакета | приватная отдача |
| `/t/{token}` | подпись в самой ссылке | **новое**: временная ссылка |
| `/web/**` | сессия админки | панель |

Однобуквенные префиксы отдачи остаются (`o` — open, `p` — private, `t` — temporary):
они попадают в чужие вёрстки и CDN, короткие — лучше.

## 2. Сущности

### 2.0 Идентификаторы: bigint внутри, slug наружу

Правило: **UUID остаётся только у `Bucket`**, все остальные таблицы — `bigint identity`.

Почему уходим от UUID в горячих таблицах. UUIDv4 случаен, поэтому каждая вставка
попадает в случайную страницу B-дерева: сплиты страниц, промахи кэша, распухший
WAL. На загрузке это не главная стоимость (запись блоба на диск дороже), но
платим мы не только на вставке — 16-байтный ключ тянется во все внешние ключи и
индексы по ним (`files.blob_id`, `files.folder_id`, `share_links.file_id`).
`bigint` вдвое меньше и плотный.

Почему у бакета UUID остаётся. Бакеты создаются редко (единицы за всё время
жизни установки), проблемы случайной вставки на такой таблице просто нет, а
готовый неперечислимый идентификатор для публичного URL — ровно то, что нужно.
Цена — `bucket_id` в дочерних таблицах остаётся 16-байтным; на фоне того, что
`files` всё равно несёт имя файла и таймстампы, это терпимо.

Почему нельзя просто заменить всё на bigint. Публичная отдача `/o` идёт **без
авторизации** — в s4w её защищали только тем, что в адресе два UUID (~244 бита,
перебор невозможен). Последовательный `1, 2, 3…` в публичном URL сделал бы чужие
файлы перечислимыми, а сквозная нумерация выдавала бы объёмы платформы.

Поэтому у `FileEntry` идентичность разводится на две:

| | тип | где живёт |
|---|---|---|
| внутренний `id` | `bigint identity` (`#[BigId]`) | PK, все FK, джойны — наружу не выходит **никогда** |
| внешний `slug` | `char(16)`, 96 бит случайности, base64url | URL и тела ответов API — единственный «id» файла для клиента |

Slug нужен только файлу: `Bucket` адресуется своим UUID, `Folder` — именем
внутри бакета, `AccessToken` — своим секретом, `Blob` наружу не выходит вообще.

Цена slug — один случайный уникальный индекс на `files` (та самая проблема
записи, но на одном индексе вместо PK и всех FK). Бонус — он короче UUID, и его
можно перевыпустить, не трогая строку и связи: мгновенный сброс всех внешних
ссылок на файл.

### 2.1 `Bucket` — пространство с квотой (было `Instance`)

**Панель работает с базой целиком.** Бакеты, папки, файлы, токены и ссылки
читаются и меняются через сервисы; на выдумке остался только обзор — сводка по
всему хранилищу, считать которую пока некому. Загрузка файла идёт настоящим
multipart через `XMLHttpRequest` (у `fetch` нет прогресса отправки), карточка
файла открывается боковой панелью, у списков серверные поиск, сортировка и
постраничность.

**Подключён к панели целиком** (`/admin/ui/buckets`): список, создание,
правка, политика кэша и удаление идут в базу, без перезагрузок страницы.
Счётчики файлов, блобов и папок считает `BucketService::stats()` — три
сгруппированных запроса на страницу, а не три на строку. Для панели заведён
отдельный вид `Main\Web\BucketView`: тащить счётчики в `BucketRes` значило бы
менять контракт API ради одной таблицы.

Появилась ручка `PATCH /admin/buckets/{id}/cache` — колонки `cache_*` у бакета
были с самого начала, а выставить их было нечем.

Зачем: единица изоляции и тарификации. Всё остальное живёт внутри бакета,
FK — `ON DELETE CASCADE`.

```
id             uuid pk        (единственная таблица с UUID — см. §2.0)
name           varchar(100)  unique
description    varchar(255)
quota_bytes    bigint        лимит
used_bytes     bigint        сумма размеров блобов (не сумма файлов — дедуп)
status         smallint      BucketStatus: CREATED|PENDING|INACTIVE|ACTIVE
cache_max_age  int  null     политика кэша по умолчанию для бакета (NULL = глобальный дефолт)
cache_visibility smallint null CacheVisibility: PUBLIC|PRIVATE|NO_STORE (NULL = вывести из public-флага файла)
link_epoch     bigint  = 1   счётчик отзыва ВСЕХ временных ссылок бакета
created_at, updated_at
```

`link_epoch` — рычаг массового отзыва: инкремент делает недействительными все
ранее выданные подписи бакета одним UPDATE, без обхода ссылок. Тот же приём, что
версия в `DeliveryCache`.

### 2.2 `Folder` — папка (было `Section`)

Зачем: группировка файлов + место, где живут политики (видимость, срок хранения, кэш).
Плоская, один уровень — как в s4w. Вложенности не будет (решено).

```
id            bigint pk identity
bucket_id     uuid   fk → buckets  (cascade)
name          varchar(100)   unique(bucket_id, name)
public        bool           файлы папки доступны через /o
retention     smallint       Retention: NONE|DAY|WEEK|MONTH|QUARTER|HALF_YEAR|YEAR
cache_max_age int  null      NULL = наследовать от бакета
cache_visibility smallint null NULL = наследовать от бакета
created_at, updated_at
```

`Retention` — фиксированная шкала, без произвольных значений: `NONE` (вечно),
`DAY`, `WEEK`, `MONTH`, `QUARTER` (3 месяца), `HALF_YEAR`, `YEAR`. Закрытый список
проще и в UI (селект), и в API (валидация), и в голове.

Корень бакета (`folder_id IS NULL`) — не строка в таблице, а отсутствие папки:
всегда `public`, без retention, кэш берётся с уровня бакета.

### 2.3 `FileEntry` — файл в папке (было `FileRecord`)

Зачем: имя + размещение + права + срок. Контент — отдельно, в `Blob`
(два файла с одинаковыми байтами делят один блоб).

```
id          bigint pk identity
slug        char(16) unique   внешний id: URL и API
bucket_id   uuid   fk → buckets (cascade)
folder_id   bigint fk → folders (cascade)  NULL = корень бакета
blob_id     bigint fk → blobs   (restrict)
name        varchar(255)
mime_type   varchar(127)  тип этого файла: Content-Type на отдаче
extension   varchar(32)   расширение, с которым файл лёг
public      bool          денормализация Folder.public — чтобы отдача не читала папку
expires_at  timestamp null денормализация Folder.retention — момент смерти файла
created_at, updated_at

unique(bucket_id, name)             where folder_id is null
unique(bucket_id, folder_id, name)  where folder_id is not null
index(expires_at)                   where expires_at is not null
```

Отличие от s4w: папка хранится как **`folder_id`, а не строка**. Переименование
папки становится одним UPDATE строки папки вместо массового апдейта всех файлов,
и имя папки перестаёт быть частью ключа файла.

`expires_at` денормализован осознанно: отдача обязана 404-ить просроченный файл
**сама**, не полагаясь на то, что уборщик уже отработал. Уборщик — про освобождение
места, а не про корректность.

`mime_type` и `extension` сначала лежали на `Blob` и переехали сюда
(`docs/migrations/2026-08-16-mime-to-files.sql`). Тип — свойство файла, а не
байтов: при дедупликации один блоб обслуживает несколько файлов, и тип первого
загрузившего навязывался всем остальным. `data.csv` и `data.txt` с одинаковым
содержимым — законная пара с разным `Content-Type`. Для форматов, которые
определяются по байтам, разницы нет; вылезало это на тексте, где тип выводится
из имени.

### 2.4 `Blob` — контент (было `FileBlob`)

Зачем: дедупликация. На диске — `storage/chest/{bucket_id}/{sha256}`, в БД — учёт ссылок.

```
id          bigint pk identity
bucket_id   uuid   fk → buckets (cascade)
hash        char(64)      unique(bucket_id, hash) — sha256 в hex, см. ниже, не hex
size_bytes  bigint
ref_count   bigint        сколько FileEntry ссылаются
created_at
```

Блоб — мешок байтов: хэш, размер и учёт ссылок. Тип и расширение живут на
`FileEntry` (см. §2.3), хотя определяются по этим же байтам — `finfo`, не по
имени.

`hash` планировался как `bytea` (32 байта вместо 64) — индекс по нему самый
горячий, lookup дедупликации идёт на каждой загрузке. **Отменено после проверки:**
через PDO сырые байты сервер отвергает (`invalid byte sequence for encoding UTF8`),
запись требует ручной hex-нотации `\x…`, а чтение возвращает resource-поток
вместо строки — то есть ломает гидрацию сущности и `SELECT *`. Цена решения —
примерно 32 лишних байта на строку в индексе. Хранится `char(64)` hex, как и на
диске (`chest/{bucket}/{hex}`).

Дедуп остаётся **в пределах бакета** — межбакетный шаринг байтов ломает изоляцию
(один арендатор узнаёт по скорости загрузки, что файл уже есть у другого).

### 2.5 `AccessToken` — токен арендатора (было `InstanceToken`)

Зачем: доступ к `/v1` и `/p` от имени бакета. В БД только sha256-хеш, сам токен
отдаётся один раз.

```
id           bigint pk identity
bucket_id    uuid   fk → buckets (cascade)
hash         char(64) unique    sha256 в hex (bytea отменён, см. §2.4)
name         varchar(100)
status       smallint  TokenStatus: INACTIVE|ACTIVE
expires_at   timestamp null   новое: срок жизни токена (NULL = бессрочно)
last_used_at timestamp null   новое: для «этот токен мёртв, можно удалять»
created_at
```

### 2.6 `ShareLink` — временная ссылка (новое)

Зачем: выдать доступ к одному файлу тому, у кого нет токена, на ограниченное время.

**Строка в БД создаётся не всегда.** Базовый режим — подпись без состояния
(§4): ничего не пишем, нечего чистить, проверка не ходит в БД. Строка нужна
только когда ссылка должна быть *отзываемой поимённо* или *с лимитом скачиваний*.

```
id             bigint pk identity   он же jti внутри подписи (8 байт вместо 16)
bucket_id      uuid   fk → buckets (cascade)
file_id        bigint fk → files   (cascade)
expires_at     timestamp
max_downloads  int  null     NULL = без лимита
downloads      int  = 0
revoked        bool = false
disposition    smallint      Disposition: INLINE|ATTACHMENT
note           varchar(255)  кому/зачем выдали — для аудита в панели
created_at

index(expires_at)
```

## 3. URL файлов

`{bucket}` — UUID бакета, `{file}` — **slug** файла (16 символов, §2.0). Хост
берётся из запроса либо из `PUBLIC_BASE_URL` (в s4w это `UPLOAD_HOST` — имя
врало: переменная задаёт базу не для загрузки, а для отдачи).

| канал | шаблон | пример |
|---|---|---|
| публичный | `/o/{bucket}/{file}` | `https://files.example.com/o/f8d91c79-6659-cbd6-882d-a7cfcc0164c3/3njpj-alg5OEZKHp` |
| приватный | `/p/{file}` | `https://files.example.com/p/3njpj-alg5OEZKHp` |
| временный | `/t/{token}` | `https://files.example.com/t/tlpLU7RMbvTdBPhSORfB4E13blt5nWhljViOz-W6edHETA` |
| временный с лимитом | `/t/{token}` | `…/t/MVOVRMUM5UU4gRDgtLY-RqF9u182MhffLPZuW3mdaGWNWI7P5bp50cRM` |
| админский | `/admin/buckets/{bucket}/files/{file}/raw` | — |

Длина временного токена фиксирована: **46 символов** без строки в БД, **56** —
с `jti` (отзыв поимённо / лимит скачиваний).

### 3.1 Папки в URL нет

Решение, отличающее s5w от s4w: сегмента папки в адресе отдачи **не будет**.

`file` уже уникален, папка в пути ничего не находит — в s4w она только
проверялась (`section !== $meta['section']` → 404) и делала ссылку ломкой:
переименовал папку или переместил файл — все внешние ссылки умерли. Раз папка
теперь `folder_id` (§2.3), её имя вообще перестало быть частью адресации.

Побочный выигрыш: приватный адрес схлопывается до `/p/{file}` — бакет и так
известен из токена.

### 3.2 Хвоста-имени не будет

Вариант `/o/{bucket}/{file}/logo.svg` (игнорируемый последний сегмент ради
читаемой ссылки) отклонён: имя файла при скачивании и так приходит в
`Content-Disposition` из БД, то есть сегмент давал бы только косметику. Если
понадобится — добавляется позже необязательным сегментом, не ломая ни одной
выданной ссылки.

### 3.3 Управление отдачей

- `?download=1` → `Content-Disposition: attachment` для `/o` и `/p`.
- Для `/t` disposition зашит в подпись (флаг в payload) — параметром его не
  подменить, потому что канал и так одноразово-настраиваемый на выпуске.

## 4. Механика: временные ссылки

### 4.1 Формат

Ссылка: `GET /t/{base64url(payload || sig)}` — один непрозрачный токен, без query-параметров
(иначе `exp`/`sig` осядут в access-логах и в чужих Referer).

`payload` (бинарь, 18 байт; 26 с `jti`):

| поле | размер | зачем |
|---|---|---|
| версия формата | 1 | ротация схемы без ломки старых ссылок |
| `file_id` | 8 | внутренний bigint файла |
| `exp` | 4 | unix-время смерти |
| `flags` | 1 | bit0 — attachment, bit1 — есть `jti` (значит, нужен поход в БД) |
| `link_epoch` | 4 | значение счётчика бакета на момент выпуска |
| `jti` | 8 | только при bit1 — id строки `ShareLink` |

Бакета в payload нет: файл однозначно задаёт свой бакет, а `link_epoch` для
сверки всё равно приходит вместе с метаданными файла из `DeliveryCache`.

Внутрь подписи кладём `id`, а не `slug`: подпись уже исключает подбор, а lookup
идёт прямо по первичному ключу, без второго индекса. Наружу это ничего не
раскрывает — payload не прочесть, не разобрав base64, а знание «это файл №417»
бесполезно, пока подпись нельзя подделать.

`sig` = первые 16 байт `HMAC-SHA256(payload, K_link)` — 128 бит стойкости, этого хватает.

Итог: 46 символов в base64url без `jti`. Ключ выводим из существующего секрета,
новый в env не заводим:

```php
K_link = hash_hmac('sha256', 'winter/s5w/link/v1', env('WINTER_KEY'), binary: true);
```

Следствие: ротация `WINTER_KEY` гасит все ссылки — это приемлемо и даже полезно.

### 4.2 Проверка (порядок важен)

1. декодировать, проверить версию и длину;
2. `exp > now` — иначе 404 (не 403: существование файла не подтверждаем);
3. `hash_equals` на подпись — **до** любого обращения к БД, чтобы неподписанный
   мусор не создавал нагрузку;
4. взять метаданные файла из `DeliveryCache` (там же `link_epoch` бакета);
   `epoch` из подписи ≠ текущему → 404;
5. `expires_at` файла (retention) прошёл → 404;
6. если bit1: прочитать `ShareLink`; `revoked`, просрочка или исчерпанный лимит → 404;
   иначе атомарный инкремент
   `UPDATE share_links SET downloads = downloads + 1 WHERE id = ? AND (max_downloads IS NULL OR downloads < max_downloads)` —
   0 затронутых строк → 404;
7. отдать через `ResponseStreamFile` с политикой кэша из §6.

**Стык с Range:** при `max_downloads` докачка/перемотка шлёт несколько запросов и
счётчик врёт. Для лимитированных ссылок вызываем `->acceptRanges(false)` —
атомарная отдача целиком, один запрос = одно скачивание. Для обычных подписанных
ссылок Range оставляем включённым.

### 4.3 API

```
POST /v1/files/{id}/link          { ttl: 3600, disposition: "inline" }
POST /v1/files/{id}/link          { ttl: 86400, maxDownloads: 3, note: "для подрядчика" }   → строка в БД
GET  /v1/links                    список выпущенных строк (только stateful)
DELETE /v1/links/{id}             отзыв конкретной ссылки
POST /v1/links/revoke-all         link_epoch++ у бакета
```
Зеркальные ручки под `/admin/buckets/{id}/...`.

## 5. Механика: папка-времянка

### 5.1 Модель

`Folder.retention` — метка срока хранения из закрытого списка:

| значение | срок |
|---|---|
| `NONE` | вечно (обычная папка) |
| `DAY` | 1 день |
| `WEEK` | 7 дней |
| `MONTH` | 1 месяц |
| `QUARTER` | 3 месяца |
| `HALF_YEAR` | 6 месяцев |
| `YEAR` | 1 год |

Срок **скользящий, у каждого файла свой**: файл живёт от момента своей загрузки
ровно `retention`. Загруженное вчера умрёт завтра, загруженное сегодня —
послезавтра. Папка целиком по расписанию не вычищается.

Интервалы считаем календарно (`created_at + interval '1 month'`), а не в
секундах — «месяц» пользователь понимает как месяц, а не как 30 суток.

### 5.2 Где считается срок

`expires_at` пишется в `FileEntry` в момент, когда файл оказывается в папке:

- загрузка в папку с retention → `expires_at = now + retention`;
- перемещение в такую папку → пересчёт от `now`;
- перемещение в папку без retention или в корень → `expires_at = NULL`;
- смена `retention` у папки → массовый пересчёт от `created_at` файлов:
  `UPDATE files SET expires_at = created_at + interval WHERE folder_id = ?`;
  снятие метки → `expires_at = NULL`. И то, и другое — инвалидация `DeliveryCache`.

### 5.3 Уборщик

`RetentionSweeper` — задача планировщика (`#[EnableScheduler]` уже есть в v4),
раз в 15 минут:

```
SELECT id, bucket_id FROM files
 WHERE expires_at IS NOT NULL AND expires_at <= now()
 ORDER BY expires_at LIMIT 500
```
дальше — общий путь удаления файла (декремент `ref_count`, возврат квоты, unlink
блоба после коммита, инвалидация кэша бакета). Батчами, чтобы длинная транзакция
не держала блокировки.

Ключевой инвариант: **просроченный файл не отдаётся, даже если уборщик ещё не
дошёл** — проверка `expires_at` встроена в `DeliveryService` и в проверку ссылки.

## 6. Механика: политика кэша

### 6.1 Разрешение (снизу вверх)

```
max_age    = folder.cache_max_age    ?? bucket.cache_max_age    ?? env(CACHE_DEFAULT_MAX_AGE, 86400)
visibility = folder.cache_visibility ?? bucket.cache_visibility ?? (file.public ? PUBLIC : PRIVATE)
```

Дальше — обязательные зажимы, они важнее настройки:

| условие | что делаем |
|---|---|
| файл не `public` | `visibility` не может быть `PUBLIC` → понижаем до `PRIVATE` |
| канал `/p` (приватная отдача) | `PRIVATE` |
| канал `/t` (временная ссылка) | `PRIVATE`, `max_age = min(max_age, exp − now)` — кэш не должен пережить ссылку |
| файл с `expires_at` (времянка) | `max_age = min(max_age, expires_at − now)` |
| `visibility = NO_STORE` | `Cache-Control: no-store`, `max_age` игнорируется |
| `public` и `max_age > 0` | добавляем `immutable` — байты по этому id не меняются (перезалива в существующий id нет) |

`ETag`/`Last-Modified` и `304` даёт сам `ResponseStreamFile`, ничего не делаем.
Реализация — `Service/CachePolicy` (чистая функция от трёх уровней + канала),
результат кладётся в `DeliveryCache` вместе с остальными метаданными, поэтому
изменение политики бакета или папки обязано бампать версию кэша бакета.

### 6.2 Настройка

```
PATCH /admin/buckets/{id}/cache        { maxAge: 3600, visibility: "public" }
PATCH /v1/folders/{name}/cache         { maxAge: null, visibility: null }   // вернуть наследование
```

Глобальные дефолты: `CACHE_DEFAULT_MAX_AGE` (86400), `CACHE_PRIVATE_MAX_AGE` (0).

## 7. Что ещё меняется по дороге

- **Отдача.** `X-Accel-Redirect` → `ResponseStreamFile::open(...)`. Требует
  доработки в самом kernel v4: фабрика берёт имя из `basename($path)` и mime из
  `mime_content_type()`, а у нас на диске файл называется sha256 без расширения —
  нужны опциональные параметры `fileName` / `mimeType`.
- **Кэш.** `FileStore` → `winter-cache` (Redis уже в зависимостях образа).
  `DeliveryCache` и `TokenCache` переезжают на него; версионная инвалидация остаётся.
- **Планировщик вместо cron.** Три `Sweeper`-а и `RetentionSweeper` — задачи
  `#[EnableScheduler]` внутри процесса, а не строки в crontab образа.
- **Счётчики отдачи.** Трафик теперь идёт через воркер (nginx его больше не
  перехватывает) — можно вести реальную статистику скачиваний и наполнить страницу
  аналитики, которая в s4w работает на моках (`resources/helpers.php`).

## 8. Порядок реализации

1. Каркас: `DbConfig`, сущности, репозитории, миграция, DI. Пустые бакеты создаются/удаляются.
2. Блобы и файлы: `BlobStore`, загрузка с дедупом, квота, коллизии имён, удаление с GC.
3. Отдача: `DeliveryService` + `/o`, `/p`, `DeliveryCache`, Range/304.
4. Токены доступа: `AccessToken`, middleware, кэш токенов.
5. **Политика кэша** (§6) — до ссылок, потому что ссылки её переиспользуют.
6. **Retention** (§5) — `expires_at`, зажим отдачи, `RetentionSweeper`.
7. **Временные ссылки** (§4) — сначала stateless, потом `ShareLink` с лимитами.
8. Админка и API: контроллеры `/admin` и `/v1`, панель.
9. Уборщики-сироты, актуатор, документация.

## 9. Решения

Принято:

- главная сущность — **`Bucket`**;
- **`WIPE` не нужен** — только скользящий TTL у каждого файла;
- `retention` — закрытая шкала **без `CUSTOM`**: день / неделя / месяц / 3 месяца / полгода / год;
- папка адресуется **`folder_id`**, строкового `section` больше нет;
- **миграции из s4w не будет** — старт с чистого листа;
- **вложенных папок не будет** — один уровень;
- **ключи**: `bigint identity` во всех таблицах, кроме `Bucket` — там остаётся
  UUID (создаются редко, зато готовый неперечислимый id для публичного URL);
  наружу файл ходит под `slug`, внутренний `id` не публикуется (§2.0).

- **лимит скачиваний `max_downloads` оставляем.** Считаем в БД атомарным UPDATE
  (§4.2), Range у таких ссылок выключен. Перенос счётчика в Redis — потом,
  отдельным тюнингом, когда всё остальное работает.

- **хвоста-имени в URL не будет** (§3.2) — `Content-Disposition` закрывает эту
  задачу, а добавить сегмент позже можно без ломки выданных ссылок.

Открытых вопросов нет — §8 можно исполнять по шагам.

## 10. Обработка изображений при загрузке — сделано

В s4w загрузка принимала `compress` (0…100, где 100 — максимальное сжатие) и
`webp` (bool). В s5w это потерялось — вернули, но в другом виде.

Код: `main/Image/ImageProcessor.php`, `main/Image/ProcessedImage.php`,
`main/Enum/ImageFormat.php`, поля в `main/Request/FileUploadRequest.php`,
вызов в `FileService::upload()`, расширения в `docker/dependencies/30-gd.sh`.

### 10.1 Параметры вместо старых двух

| поле формы | тип | по умолчанию | смысл |
|---|---|---|---|
| `format` | enum | `ORIGINAL` | `ORIGINAL` \| `WEBP` \| `JPEG` \| `PNG` \| `AVIF` — в какой формат перекодировать |
| `quality` | 1…100 | по формату | качество кодека; выше — лучше. Дефолт нужен только когда перекодирование и так идёт: webp/jpeg 82, avif 55, png 60 |
| `maxWidth` | 16…10000 | — | уменьшить, если шире; пропорции сохраняются |
| `maxHeight` | 16…10000 | — | то же по высоте |

Оси независимы, но связаны одним правилом: перекодирование происходит, если
попросили формат, качество или ресайз. `format=JPEG` на jpeg без остального —
это `nothing to do`, файл не открывается.

Три изменения против s4w:

1. **`quality` вместо `compress`.** У s4w шкала перевёрнута (`compress=100` —
   максимальное сжатие, внутри `quality = 100 - compress`), и это ровно тот
   параметр, который все остальные инструменты называют качеством. Инверсия в
   API — источник ошибок на стороне клиента.
2. **`format` вместо `webp: bool`.** Следующий вопрос после webp — «а avif?»,
   и добавлять второй флаг рядом с первым уже поздно.
3. **Появился ресайз.** Это главное, чего не хватало: хранилищу почти всегда
   нужен не «пожать байты», а «не держать фотографию 6000×4000 в аватарке».

Ничего не задано — файл кладётся как есть, байт в байт.

### 10.2 Где это живёт

Новый `main/Image/ImageProcessor.php`: получает путь временного файла и опции,
возвращает путь нового временного файла (или тот же, если делать нечего).
Вызывается из `FileService::upload()` **до** `BlobService::store()`.

`BlobService` не меняется вообще: он и так получает временный файл, считает от
него sha256 и определяет тип. Дедупликация автоматически идёт по *обработанным*
байтам — два одинаковых исходника с разными `quality` дадут два блоба, и это
правильно: содержимое разное.

`FileRes` получает блок `processed`: что применили, исходный размер, итоговые
размеры. Клиент должен видеть, что байты на сервере — не те, что он отправил.

Имя файла идёт за содержимым — `FileService::finalName()`:

1. расширение совпадает с содержимым (с точностью до написания: `jpeg`/`jpg`,
   `htm`/`html`, `yml`/`yaml`) — имя не трогаем;
2. противоречит и похоже на указание типа (`ContentType::isKnownExtension()`) —
   заменяем: `photo.jpg` → webp даёт `photo.webp`, а jpeg с именем
   `mislabeled.png` ложится как `mislabeled.jpg`;
3. иначе дописываем: `отчёт v1.2` → `отчёт v1.2.pdf`.

Правило общее, не только для картинок: до него `photo.jpeg` превращался в
`photo.jpeg.jpg`. У текста расширение по-прежнему берётся из имени — finfo видит
«# заголовок» как markdown, но переименовывать чужой `.txt` мы не вправе.

### 10.3 Расширения в образе

Ни `gd`, ни `imagick`, ни `exif` в базовом образе не было — добавлены в
`docker/dependencies/30-gd.sh` (gd с jpeg/png/webp/avif + exif). Если расширения
нет, обработка отвечает 501, а не падает.

**После `docker compose build` проверить:**

```
docker exec s5w php -r 'print_r(gd_info());'   → WebP Support: 1, AVIF Support: 1
```

### 10.4 Ограничения, без которых нельзя

- **Пиксельный потолок** — `MAX_PIXELS = 25 Мп`. GD разворачивает картинку в
  несжатый bitmap по 4 байта на пиксель, а поворот на время работы удваивает
  это: 25 Мп — 100 МБ на кадр, 200 МБ на пике при `memory_limit=256M`. Размеры
  берём из `getimagesize()` (читает только заголовок) **до** декодирования,
  иначе — 422. Это же защита от «декомпрессионной бомбы»: файл на 40 КБ с
  холстом 30000×30000.
- **EXIF-ориентация.** Фото с телефона хранится повёрнутым, поворот лежит в
  EXIF. GD его не применяет, а при перекодировании метаданные теряются —
  картинка ляжет набок. Разворот делаем **после** ресайза (на уменьшенном кадре
  он дешевле), а рамку `maxWidth`/`maxHeight` заранее меняем местами, если
  ориентация меняет стороны — результат тот же, пик по памяти ниже.
- **Анимация.** GD схлопывает анимированный GIF/WebP в первый кадр. Такие файлы
  не трогаем вовсе (кладём как есть) и говорим об этом в ответе: `reason:
  animated`. Определяем по контейнеру — второй GCE у GIF (потоком, первый кадр
  может весить мегабайты), флаг ANIM в VP8X у WebP, чанк `acTL` у APNG.
- **Реэнкод в минус.** Если формат и геометрия не менялись, а результат вышел
  не меньше исходника (обычное дело у PNG), отдаём оригинал с `reason: output is
  larger than source`. Просьбу сменить формат или размер это правило не трогает.
- **PNG.** `quality` для PNG — не потери, а уровень zlib; лоссёвого PNG без
  квантизации не бывает. Для фотографий предлагаем webp, а не «пожатый PNG».
- **Swoole блокируется.** GD — синхронный CPU-код внутри воркера: секунда
  ресайза это секунда простоя его корутин. Для первой версии принимаем как
  есть (потолок по пикселям ограничивает худший случай), дальше — вынести в
  `#[EnableProcess]`-воркер или executor.

### 10.5 Что осознанно откладываем

- **Варианты по запросу** (`/o/{bucket}/{slug}?preset=thumb`) — то, ради чего
  обычно и заводят обработку. Нужен отдельный кэш производных, его
  инвалидация и **закрытый список пресетов**: свободные `?w=&h=` превращают
  отдачу в генератор нагрузки и мусора в кэше. Отдельная фаза.
- **Политика обработки на папке** — «в `images` всё приводится к webp 2000px
  q82». Ложится ровно в текущую модель (папка уже держит видимость, срок и
  кэш), но делать имеет смысл после того, как заработает разовая обработка.

### 10.6 Что проверено

Обработчик отдельно (17 сценариев) и загрузка целиком — через `FileService` на
временной базе (13 проверок):

- `jpeg → webp 512px q80`, байты на диске действительно webp;
- только `quality` — формат прежний, файл меньше;
- рамка больше картинки и `format=JPEG` на jpeg — `nothing to do`;
- вписывание в рамку по меньшей стороне (`300×100` для 3:2 → `150×100`);
- прозрачный png → webp: альфа на месте; png → jpeg: фон белый, не чёрный;
- реэнкод толще исходника → оригинал, временный файл убран;
- анимированный gif не тронут, статичный — обработан;
- бомба 30000×30000 → 422, не картинка → 422;
- EXIF Orientation=6: кадр развёрнут, рамка ресайза посчитана после разворота;
- сквозь `FileService`: имя стало `photo.webp`, хэш на диске сходится с базой,
  повтор тех же параметров дал дедупликацию, `used_bytes` равен сумме блобов.

### 10.7 Что осталось на потом

- `imagedestroy()` в PHP 8.5 объявлен устаревшим и с 8.0 ничего не делает —
  кадры освобождает счётчик ссылок. Нигде не зовём.
- Вынести GD из воркера, если ресайз начнёт заметно держать корутины.
