# Redis в s5w — сырая идея

Черновик, не решение. Записано 21.08.2026, чтобы не потерять.

## Что померили (это важнее выводов)

```
db ping до 62.113.58.80        22–27 мс   ← включает установку соединения
TCP-рукопожатие туда же         1.9 мс    ← медиана 7 замеров
```

22 мс — это TCP + startup/auth Postgres, и платит их пул один раз, а не каждый
запрос (`minimumIdle = 2` держит соединения тёплыми). На прогретом соединении
запрос стоит ~2 мс сети.

Отсюда:

- выдача `/o/{bucket}/{slug}` делает 4 последовательных запроса (`files`,
  `buckets`, `folders`, `blobs`) ≈ 8 мс сети;
- API-запрос делает 1 (проверка токена) ≈ 2 мс;
- Redis на **том же хосте**, его GET стоит те же ~2 мс.

**Вывод, который убивает половину идеи:** кэш выдачи экономит ~6 мс на
скачивание. Ради этого зависимость не тащат. Аргумент за кэш остаётся только
один, и он на будущее: 4 заимствования из пула на запрос при пуле в 10 —
это то, что упрётся первым, когда вырастет трафик. То есть кэш про нагрузку
на Postgres, а не про миллисекунды клиенту.

## Единственное, что Redis тут даёт по-настоящему: квота на токен

Этого у сервиса нет и без общего состояния быть не может. `maxConcurrency` из
ядра — очередь на воркер: он не знает, кто звонит, и не умеет ответить `429`.
Сейчас один токен может молотить API и жечь исходящий трафик сколько угодно.

Набросок:

```php
final class RateLimitStore extends RedisStore
{
    protected string $redisConfigClassName = MainRedisConfig::class;
    protected string $prefix = 'rl:';

    public function hit(int $tokenId, int $window = 60): int
    {
        $key  = $tokenId . ':' . intdiv(time(), $window);
        $hits = $this->increment($key);
        if ($hits === 1) {
            // Срок ставим только на первом попадании — иначе окно ползёт вперёд
            // и не закрывается никогда.
            $this->raw()->expire($this->key($key), $window + 1);
        }
        return $hits;
    }
}
```

Вызов — в `AccessTokenMiddleware`, сразу после проверки токена. Превысил →
`429` + `Retry-After`. Лимит хранить полем в `access_tokens`, а не константой.

Два решения, которые надо помнить:

- **Окно фиксированное, не скользящее.** На стыке окон клиент может выдать
  двойную норму. Скользящее — это sorted set и три команды вместо одной. Для
  защиты от «забыли убрать цикл» фиксированного хватает.
- **Redis упал → пропускаем.** Ограничитель, который при недоступности своего
  хранилища закрывает дверь, превращает аварию Redis в аварию сервиса. Раздача
  файлов важнее квоты.

## Подключение

Конфиг по образцу `MainDbConfig` — хост удалённый, значит те же
`keepaliveTime` / `idleTimeout` / `minimumIdle`. Плюс своё:

- `poolWaitTimeout = 0.2`, `timeout = 0.3`, `readTimeout = 0.5` — Redis не имеет
  права задерживать запрос дольше, чем стоил бы обход мимо него;
- отдельный `databaseIndex` (`REDIS_DB`) — хост общий с другими проектами,
  префикса стора мало;
- `SERIALIZER_NONE`, JSON кладём сами: PHP-сериализация завязала бы формат кэша
  на форму классов и сделала бы содержимое нечитаемым из `redis-cli`.

Обязательна обёртка `SafeStore`: Redis не источник истины, а ускоритель, его
падение должно быть незаметным. Ловить **только** `RedisPoolException`,
`RedisCommandException`, `\RedisException` — не `\Throwable`, иначе обёртка
проглотит наши собственные ошибки. И предохранитель: после 3 отказов подряд не
ходить туда 10 секунд, иначе упавший Redis стоит `poolWaitTimeout` на каждом
запросе, то есть авария превращается в замедление всего.

## Куда Redis не пойдёт

| | почему |
|---|---|
| сессии загрузки | состояние транзакционное, должно пережить перезапуск |
| счётчик скачиваний ссылки | лимит обязан быть точным, `FOR UPDATE` для этого и есть |
| `used_bytes`, квота | это про деньги, а не про кэш |
| замок уборщика | файловый `SweepLock` верен, пока контейнер один; появится второй — переносим, и тогда обязательно |

## Кэш выдачи — если когда-нибудь

В ключе `deliver:{bucketId}:{slug}` лежал бы флаг `public`, то есть **решение о
доступе**. Протухший ключ — это не «немного старые данные», а закрытый файл,
отданный по публичной ссылке. Инвалидация должна быть явной и полной: правка
файла, перемещение в папку, смена флага папки, смена политики бакета, смена
`link_epoch`, удаление. Пропустили один путь записи — получили неправильный
ответ, а не медленный. Браться только вместе с прогоном, который проверяет
каждый путь записи на чистку кэша.
